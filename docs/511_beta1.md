# 511 β1 運用ガイド

基準は `511_BETA1_SPEC_v1.0.md` と利用者が確定したBLOCKER規則。
511は既存4戦略CSVのOPENを入力とするShadow専用レイヤー。
実注文・自動Live昇格・過去成績による条件変更は行わない。

## 固定Research条件

- Unique Event: symbol × direction × JST 5分bucket。LONG/SHORTは別。
- PULLBACKあり: 最も早いPULLBACK行のentry。なし: 最も早い戦略行。
  同時刻はstrategy名・row hashの固定順。重複PULLBACKは監査記録。
- Crowding: 現在bucketを除く直前6完成bucketのUnique LONG/SHORT件数。
  同数・0件はNEUTRAL。それ以外は現在方向とのMATCH/OPPOSITE。
- Persistence: 6bucketのうち30分多数方向と一致するbucket数。LOW=0–2、MID=3–4、HIGH=5–6。
- `CORE_B1_PULLBACK_OPPOSITE`: has_pullback AND OPPOSITE。AssetやPersistenceで絞らない。
- Challenger: Core AND LOW、Core AND (CRYPTO_NATIVE/COMMODITY_LINKED)、Core ANDその両方。
- Control: PULLBACK_ANY、OPPOSITE_ANY、OPPOSITE_NON_PULLBACK、PULLBACK_MATCH、
  TREND_VOLUME、OI_FUNDING、HIGH_EDGE（モデルIDはそれぞれCTRL_接頭辞）。
- SL=0.5%、TP=0.5%、RR=1、最大3時間、1 Event=1R。同じEventのモデル間で価格Pathを共有。

## 起動方法

Python 3.11と `requirements.txt` の依存を用意し、リポジトリルートから実行する。

```sh
python -B -m unittest discover -s tests/model511 -v
python -B -m model511 --mode BACKFILL --as-of 2026-09-25T06:00:00+09:00 --output-dir work/511_validation
```

BACKFILLは実装確認専用。実データのbars/observationsがある場合だけ
`--market-file recorded_market.json` を指定する。未指定ならEvent/Trade生成のみで、
市場価格を捏造しない。BACKFILLでライブ価格取得は不可。
全過去CSVの一括投入は当時の到着順を再現しないためForward成績ではない。

FORWARDは実装コミット確定後、4戦略が同一Scanner出力を処理した環境で起動する。

```sh
python -B -m model511 --mode FORWARD --verify-strategy-states --fetch-market
```

Actionsはさらに `--run-start` に当該実行の開始時刻を渡し、Scanner出力の鮮度を検証する。
ローカルに最新Scanner出力がなければこの検証は失敗する。欠損を偽データで埋めない。
FORWARDで `--as-of` は使用不可。初回稼働後の次の5分境界を `forward_start_jst` として固定。
それ以前のEventはCrowdingの初期履歴だけに使用し、Forward取引に含めない。
`git_commit_hash`、`spec_version=1.0`、`spec_hash` を記録する。
未コミット状態での本番FORWARD開始は避ける（CLIはdirty treeを自動拒否しない）。

SHAKEDOWN: 2026-09-30 23:59 JSTまで。
MAIN_FORWARD: 2026-10-01 00:00以上、2026-10-15 00:00未満。
それ以降はPOST_FORWARD。成績に応じたルール変更・Live昇格はない。

## 出力とstate

標準保存先は `511_data/backfill/` と `511_data/forward/`。混用しない。

| ファイル | 内容 |
|---|---|
| 511_state.json | 正本。Event、Membership、Open Trade、結果、quote観測、入力manifest、監査、処理済みbucket |
| 511_unique_events.csv | 1 Unique Eventにつき1行 |
| 511_model_membership.csv | Event × Model、eligibleと理由 |
| 511_shadow_trades.csv | Eventにつき共通Reference Trade |
| 511_shadow_results.csv | 固定Research結果と分離されたExecution/Cost列 |
| 511_execution.csv | Entry/Exit quote、timestamp、data age、Cost成分 |
| 511_report.csv | モデル別・モード別・期間別の集計とcoverage |
| 511_audit.log | 異常行、後着、取得失敗等のJSON Lines |

JSONは一時ファイルへの書込・flush・fsync・os.replaceで置換し、その後CSVを再生成する。
複数CSV全体が同時に置換されるわけではない。途中停止時はJSONが正本。
OSの排他lockで同じ保存先のwriterを1つに制限する。
同一入力の再処理でEvent/Membership/Tradeを追加しない。入力snapshot監査履歴は追加され得る。

## Late Dataと欠損

bucket終了後に利用できるsnapshotで確定する。確定後の新規行はLATE_ARRIVING_DATAとして保存し、
過去Event、Crowding、Membershipを書き換えない。時刻不正を別の時刻で補完しない。
4ファイルの欠損・壊れたschemaは失敗として扱い、Signalゼロとはみなさない。
ForwardのCrowdingに関係する異常行はsnapshot確定を停止する。
BTC/OI等の補助情報欠損だけでCoreから除外しない。

## Exit境界とUNKNOWN

Research entryは戦略記録のReference entry。TP/SL価格はReference価格であり実約定価格ではない。
判定はentry以後の最初の完全5分足から行う。未確定足・履歴gapは勝手に補完しない。
同一足TP/SL両到達はUNKNOWN（ambiguous_intrabar=1）。

deadline=T0+3hをまたぐ足のHigh/Lowだけで期限前到達を判定しない。
実際の細粒度データで期限前の到達を確定できる場合のみTP/SLを決定。
全体がTP/SLに触れないため期限前非到達を証明できる場合はTIMEへ進める。
判別不能ならUNKNOWN、ambiguous_deadline_boundary=1、
unknown_reason=DEADLINE_BOUNDARY_INSUFFICIENT_GRANULARITY。
TIMEにはdeadline以降の最初の利用可能な実価格観測とsource/timestampを使う。
期限前closeで代用しない。UNKNOWNの監査用TIME価格は正式結果を変えない。
UNKNOWNはPrimary EVの損益・分母から除外し、件数・割合を表示する。
一度確定したResearch/Execution結果は後着データや設定変更で再計算しない。

## ExecutionとCost

`--cost-config costs.json` で以下の実際の設定を与える（未確定値は省略する）。
`fee_bps_entry`、`fee_bps_exit`、`slippage_bps_entry`、`slippage_bps_exit`。
0は明示的な0設定のときだけ有効。システムに既定手数料・Slippage値はない。

Entry想定価格は戦略CSVの実quoteが有効な場合にLONG=ask、SHORT=bid。
そのtimestampとdecision時点でのdata ageを保存し、存在しないquoteは作らない。
ExitはReference結果timestamp以降、判定時点までに記録された最初の有効bid/askを使用可能。
LONG=bid、SHORT=ask。TP/SLもこの経路で評価する。未来quote・期限前quoteでの補完はしない。
`exit_quote_timestamp`、`execution_decision_time`、`exit_data_age_ms`、
`exit_quote_delay_ms`、`exit_bid`、`exit_ask`、`exit_expected_fill_price` を別列に保存する。
足の終了timestampは閾値到達の正確な時刻ではない。遅延quoteを閾値到達時quoteと偽らない。

E=Reference entry、X=Reference exit、Fe/Fx=観測quoteによるEntry/Exit想定価格、
s=LONGなら1、SHORTなら-1、R0=E×0.005とする。

```text
gross_R    = s × (X - E) / R0
spread_R   = s × ((Fe - E) + (X - Fx)) / R0
fee_R      = (Fe × fee_bps_entry + Fx × fee_bps_exit) / 10000 / R0
slippage_R = (Fe × slippage_bps_entry + Fx × slippage_bps_exit) / 10000 / R0
net_R      = gross_R - spread_R - fee_R - slippage_R
```

spread_Rは既存規約の「Referenceと観測Execution価格の差」で、遅延による価格変動も含む。
純粋なbid/ask幅だけの値ではないため `spread_definition` と遅延を記録する。
代数的に同等なfills方式では s×(Fx-Fe)/R0 からFee/Slippageだけを引き、Spreadを再控除しない。

各成分を独立計算する。Fee未設定でもquoteがあればSpread、Slippage設定があればSlippageを保存。
Fee/Slippageの金額基準は従来どおり実quoteに基づく想定notional。
設定値だけあってもFe/Fxが不明ならその金額成分はNULL（設定自体はcost_settingsに保存）。
必要成分のどれかが欠ければ正式Net=NULL。部分費用だけ引いた値は正式Netにしない。
BACKFILLのquote欠損はそのまま残し、Spread推計・補完をしない。

coverageはresolved_gross_n、net_evaluable_n、net_coverage_ratioで表示。
UNKNOWNをcoverage分母に入れず、解決済Grossが0なら比率はNULL。
従来の完全性条件を維持し、resolved Gross全件でNetが揃わない限り正式net_EVをNULLにする。
任意のcoverage閾値を追加しない。GrossだけでNEGATIVE/FORWARD_SUPPORTEDを判定しない。
支持判定にはさらにCore resolved>=100、30m clusters>=30、net_EV>0、95% CI下限>0が必要。

## Assetと記述的Walk-forward

信頼できる出典・version付きMappingだけを `--asset-map` で指定する。
未指定・未登録銘柄はUNKNOWN。名前推測や過去成績によるAsset選択はしない。

`--report-blocks blocks.json` は名前付き期間のJSON配列。
以下の例は開始を含み終了を含まないJST区間で、entry_time_jstによって分類する。

```json
[{"name":"week1","start":"2026-10-01T00:00:00+09:00","end":"2026-10-08T00:00:00+09:00"},
 {"name":"week2","start":"2026-10-08T00:00:00+09:00","end":"2026-10-15T00:00:00+09:00"}]
```

stateを変更せずに保存済み結果をレポートする方法:

```sh
python -B -m model511.evaluation --state 511_data/forward/511_state.json --blocks blocks.json --slices date direction asset_class
```

JSONを標準出力する。blockはDESCRIPTIVE_BLOCK_ONLY、sliceはDESCRIPTIVE_SLICE_ONLY。
モデル・BACKFILL/FORWARD・SHAKEDOWN/MAIN_FORWARDを混ぜない。
blockの重複指定はそれぞれ独立した記述集計であり、合算しない。
期間成績による条件変更やモデル選択はない。通常実行でCSVにも必要なら毎回report-blocksを指定する。

## Workflowと障害復旧

既存順序: Research Scanner → HIGH_EDGE → TREND_VOLUME → PULLBACK → OI_FUNDING
→ 511 → Exit Research。既存Research Logicは変更しない。
511処理失敗でもExit Researchに進み、4戦略完了時は既存Research保存を試みる。

1. 511専用archiveを作る。このstepはcontinue-on-error。
2. resetを伴う既存保存の前に511生データとarchiveをrecovery artifactへ退避。
3. 既存Research保存を独立実行。511のarchive・競合判定はこの処理に含めない。
4. 既存保存とarchive成功時だけ511保存を別stepで実施。
   511のリモート変更があれば上書きせず停止し、監査・archiveを残す。
5. save audit artifactを保存し、511失敗を最終stepでfailureとして報告する。

workflow_saveのsaveコマンドはActions用でcommit/pushを行う。ローカル検証では実行しない。
アーカイブ・artifact転送自体が失敗する場合もあり、転送成功はActions画面で確認する。
既存Research保存自体のネットワーク障害まで成功保証するものではない。

通常再起動: 同じmode・source・output-dirを使用する。stateを消してやり直さない。
CSV出力途中の停止: writer停止を確認し、正本JSONからCSVを再生成する。

```sh
python -B -c "from pathlib import Path; from model511.storage import lock,read,export; p=Path('511_data/forward'); exec('with lock(p):\n s=read(p,\"FORWARD\",\"recovery\"); export(p,s)')"
```

state破損・spec/mode不一致: 自動初期化しない。最後の正常JSONまたはartifactを別場所へ展開して確認する。
競合: remote stateとrecovery archiveの入力cutoff・Event ID・commitを比較し、正本を人が確認する。
異なるstateを自動結合・リセットしない。正本確定後にのみ同じ保存先で再開する。
設定不足: 実値が確定してから設定する。既に確定した結果を後からNetで埋め直さない。
Missing Scanner output: 正常なScanner→4戦略実行で揃える。検証を無効化して本番開始しない。
研究条件や結果を変更する新しい判断はBLOCKERとして扱う。
